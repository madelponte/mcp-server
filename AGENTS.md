# AGENTS.md

Repository guidance for coding agents and contributors.

## What this is

A single [FastMCP v4](https://github.com/jlowin/fastmcp) server that bundles five tool groups — **Agentic Web Search** (the `search_web` and `fetch_page` tools, where `fetch_page` also returns **YouTube** video transcripts), **Stock Data**, **Wolfram Alpha**, **Geocoding & Place Search** (OpenStreetMap Nominatim + Overpass), and **Email** (`send_email`, send-only SMTP) — originally written as Open WebUI tools and ported to MCP. Default transport is `streamable-http`, reachable at `http://<host>:8000/mcp`.

Configuration is **one YAML file** (`config.example.yaml` documents every key; `config.yaml` is the gitignored live copy, bind-mounted at `/app/config.yaml` in the container), with the legacy per-setting environment variables still working as an override layer on top of it.

The web tool group has two registered modules, `tools/web_search.py` and `tools/fetch_page.py`, plus helpers. `tools/web_fetch.py` owns SSRF-guarded provider transports, streamed direct-resource probing, Tika extraction, and the raw page cache. `tools/page_acquire.py` owns fetch_page's browser-first acquisition policy (FlareSolverr, quality assessment, optional hedged Firecrawl, and the host circuit breaker); `tools/page_quality.py` contains the deterministic quality gate and optional OpenAI-compatible classifier. `tools/web_extract.py` contains pure HTML→content helpers: markdown/plain-text rendering, structured metadata, single-section extraction, and reference-link resolution — `[12]`-style in-page citation markers are rewritten to their footnote's external source URL so a model can follow a page's references; the structured `description` falls back to JSON-LD and `toc` is the heading outline.

YouTube transcript retrieval used to be its own tool; it was folded into `fetch_page` (which detects a YouTube video URL and returns the transcript) so a model has one fewer tool to choose between. The logic still lives in `tools/youtube_transcript.py`, now exposed as the `fetch_transcript` / `is_youtube_video_url` helpers rather than a registered tool.

## Commands

```bash
# Run locally (default streamable-http transport)
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp config.example.yaml config.yaml   # then edit it
python server.py                    # finds config.yaml next to server.py

# Point at a different file (an explicitly named file must exist)
MCP_CONFIG_FILE=/path/to/other.yaml python server.py

# Run as a stdio MCP server instead (no network, no auth)
MCP_TRANSPORT=stdio python server.py    # or server.transport: stdio

# Full stack incl. fetch-page support services (FlareSolverr and Tika)
docker compose up           # mounts ./config.yaml read-only; MCP at http://localhost:8000/mcp

# Server-only image (non-web tools have no local-service deps)
docker build -t openwebui-tools-mcp .
docker run --rm -p 8000:8000 -v "$PWD/config.yaml:/app/config.yaml:ro" openwebui-tools-mcp
```

### Tests

```bash
pip install -r requirements-dev.txt   # adds pytest to the runtime deps
pytest                                 # run the whole suite (config in pytest.ini)
pytest tests/test_stock_data.py        # one module
pytest -k clamp                        # by keyword
```

The suite under `tests/` is **offline and deterministic** — no real network, no live API keys. It may load the repo's own `config.yaml` (like production) but never asserts on a configured value: caps are read from the live `cfg` at runtime, and anything a test needs pinned is `monkeypatch`ed. Tests of the loader itself (`tests/test_config.py`) always pass an explicit `path` and `env` mapping to `config.load_config`, so a live file with real credentials cannot influence them (and they never touch the process environment). Conventions, established in `tests/conftest.py`:

- **Async without a plugin.** Tests are plain sync functions that drive coroutines with the `run()` helper (`asyncio.run`). There is intentionally no `pytest-asyncio` dependency.
- **Mocked HTTP.** The `patch_httpx` fixture swaps `httpx.AsyncClient` for one backed by an `httpx.MockTransport` handler, so code that builds its own client (Wolfram, geocoding, web search, and SSRF-guarded fetches) is exercised without a socket. Sync clients (`requests` in stock data and streaming `httpx` calls to Tika) are monkeypatched per test.
- **Tool closures.** A registered tool's raw function is reached via `tool.fn` (the `tool_fns` fixture maps every tool name to it): calling it returns the JSON string on success and raises `ToolError` on failure, bypassing MCP serialization. `Tool.run()` is exercised once in `test_server.py` (note it re-raises `ToolError`; the isError wrapping happens at the server request layer, not here).
- **What's covered.** Pure helpers (cache, serialization, web extraction, fetch-page helpers, geocoding/stock/web-search math and clamping, YouTube URL parsing), the SSRF guard, page quality/Tika detection, the config loader (file discovery, env precedence, unknown keys, malformed YAML, fail-fast ranges, named auth tokens), the bearer-auth middleware (including multiple named tokens), each tool's validation and happy path against mocked providers, and server wiring (tool registration and dynamic cap interpolation in descriptions).

CI (`.github/workflows/`) runs the test suite on Python 3.13 and 3.14 before building/publishing the Docker image. A separate security workflow runs CodeQL and scans the published image with Trivy. There is no linter or formatter configured.

## Architecture

**Entry point → registration.** `server.py:build_server()` constructs one `FastMCP` instance and calls `register(mcp)` on each enabled tool module in `tools/`; the exact-name flags in `ToolSettings` (for example, `SEARCH_WEB_ENABLED`) default to true and disabled tools are omitted from registration. It is called from `__main__` (and by `scripts/show_tool.py`), never at module import time — importing `server` loads configuration and tool modules but does not construct or register a `FastMCP` instance. `run_http()` builds FastMCP's Starlette app itself and wraps it in two pure-ASGI layers: `auth.py:BearerAuthMiddleware` (bearer token) and `server.py:_LifespanCleanup`, which runs each client-owning module's `close_clients()` (`web_fetch`, `web_search`, `geocoding`, `wolfram_alpha`) on the lifespan shutdown message so the shared httpx keep-alive pools are released on a graceful stop. Non-lifespan scopes pass through untouched. Every registered tool module exposes a single `register(mcp: FastMCP)` function that defines its `@mcp.tool()` functions inside that call (closures over module-level config/cache): `web_search`, `fetch_page`, `stock_data`, `wolfram_alpha`, `geocoding`, and `email`. To add a tool group: create `tools/<name>.py` with a `register`, then wire it into `tools/__init__.py` and the import + `register()` calls in `server.py`. Helper modules have no `register`: `youtube_transcript` is consumed by `fetch_page`; `web_fetch` and `web_extract` support the web tools; `page_acquire` and `page_quality` own HTML acquisition and assessment; and `cache` / `serialize` provide shared infrastructure.

**Config is one YAML file, one pydantic model per section.** `config.py` defines a `BaseSection` (`pydantic.BaseModel`, `extra="ignore"`) per tool group — `ToolSettings`, `ServerSettings`, `WebSearchSettings`, `StockSettings`, `WolframSettings`, `YouTubeSettings`, `GeocodingSettings`, `EmailSettings` — registered in `config.SECTIONS` under the top-level YAML key that holds it (`tools:`, `server:`, `web_search:`, `stock:`, `wolfram:`, `youtube:`, `geocoding:`, `email:`). Each class records its legacy env prefix in `_env_prefix` (`MCP_`, `WEB_SEARCH_`, `STOCK_`, `WOLFRAM_`, `YOUTUBE_`, `GEO_`, `EMAIL_`; `ToolSettings` uses `""` because its fields already contain complete MCP tool names, giving flags like `SEARCH_WEB_ENABLED`). Field names **are** the YAML keys, so a section's env override is always `PREFIX + KEY.upper()` (`web_search.brave_api_key` ⇄ `WEB_SEARCH_BRAVE_API_KEY`) — that mapping is what keeps the pre-YAML variables working, and it is derived, not hand-listed. `load_config()` merges YAML + env into `AppConfig`, and the module instantiates the singletons (`tool_settings`, `server_settings`, `web_search_settings`, …) that the server/tool modules import; those names and attributes are the tool-facing API, so tools never change when the format does.

- **Discovery:** `$MCP_CONFIG_FILE` (must exist — a typo is a startup error, never a silent default-config boot), else `config.yaml`/`config.yml` next to `config.py` (**not** the CWD, so starting elsewhere can't drop the config), else `/etc/mcp-server/config.yaml`. No file at all is allowed (defaults + `CONFIG_PATH is None`), and HTTP stays fail-closed.
- **Precedence:** env → YAML → field default. A variable holding only whitespace counts as unset so a stray `FOO=` can't wipe a configured value. Nested/list fields (e.g. `server.auth_tokens`) are YAML-only.
- **Validation:** `config.example.yaml` is the canonical documented list (keep it in sync when adding a setting; `tests/test_config.py` loads it and asserts zero unknown-key warnings). Numeric fields carry range constraints (`ge=`/`gt=`/`le=`) so a cap that would silently disable or break behavior fails fast at startup with `ConfigError` naming the section, key, and — when it came from a variable — which one. Preserve this for new numeric settings (documented `0` opt-outs like cache TTLs keep `ge=0`). Unknown keys *warn* rather than fail, so an older file still starts a newer server; blank/badly-typed auth tokens are hard errors. `_list_join_fields` marks keys that accept a YAML list and are joined into the comma-separated string the consuming code parses.
- **When adding a setting:** add the `Field` (with a description) to the relevant class and document it in `config.example.yaml`. Don't read `os.environ` directly, and don't reintroduce `pydantic-settings`.

**Transport & auth.** `server.py:run_http()` builds FastMCP's Starlette app itself (rather than `mcp.run()`) so it can wrap it in `auth.py:BearerAuthMiddleware` before handing it to uvicorn. Auth is any number of **named** secrets (`server.auth_tokens`, each `{name, token}`; the legacy single `server.auth_token` / `MCP_AUTH_TOKEN` folds in as a client named `default`), enforced as pure ASGI middleware: any configured token authenticates, every entry is compared (constant-time, no early exit) so timing reveals neither which entry matched nor how close a guess was, and the matched name is stored on `scope["state"]["mcp_client"]` and logged so clients are distinguishable. Duplicate token names are a startup error (they would make the log ambiguous); duplicate token *values* collapse to one entry, and blank/non-ASCII tokens are rejected by `config.AuthToken`. HTTP transports are fail-closed: no configured token is a startup error unless `allow_unauthenticated: true` / `MCP_ALLOW_UNAUTHENTICATED=true` (which logs a warning). The `stdio` transport bypasses all of this (no network surface).

**Caching.** `tools/cache.py:TTLCache` is a tiny, dependency-free, process-local TTL/LRU cache (`OrderedDict` + monotonic timestamps + a lock for stock worker threads). Each tool that caches instantiates its own at module scope from its config's `cache_ttl_seconds` / `cache_max_entries`. `ttl <= 0` disables caching; `max_entries == 0` is unbounded, with expired entries reclaimed on later writes. Successful reads refresh recency. Cache keys must include everything that affects the result (e.g. Wolfram keys on input+assumption+units+maxchars) but **never** secrets like API keys. The raw page cache also skips individual entries above `WEB_SEARCH_CACHE_MAX_ITEM_BYTES`, so its entry-count bound cannot retain many near-`MAX_DOWNLOAD_BYTES` documents at once. Separately, FastMCP advertises a client-side component-catalog cache hint from `MCP_TOOL_CATALOG_CACHE_TTL_SECONDS` / `MCP_TOOL_CATALOG_CACHE_SCOPE`; this only covers cacheable metadata such as `tools/list`, never tool-call results.

## Conventions to follow

**Error handling — this is the core contract.** Every genuine failure raises `ToolError` (from `fastmcp.exceptions`), which FastMCP turns into a result with `isError: true`. This deliberately prevents a model from mistaking a failure for real data. A *valid-but-empty* result (a search with zero hits, a successful call that found nothing) is **not** a failure — return it as normal output. For multi-part calls like `get_company_data`, partial success returns the data plus an `errors` map; only raise `ToolError` when *everything* requested failed.

**Context-budget caps.** List/range parameters exposed to the model (result counts, financial periods, enrichment/lookback windows like `news_days`, etc.) are **maximums, not fixed amounts**. The model may request fewer; anything above the server-configured cap is silently clamped so an oversized response can't blow up the model's context window. Omitting the value uses the cap. Preserve this clamping pattern when adding parameters. Where a cap would otherwise *drop* data the model still needs (page content truncated to `WEB_SEARCH_MAX_PAGE_CHARS`), pair it with a continuation escape hatch instead of losing the rest: `fetch_page`'s `offset` param pages through truncated `content` (`_set_content` echoes a `next_offset` to re-request with), guaranteeing the rest of *any* format is reachable — including JSON and headingless docs that `query=`/`section=` can't narrow.

**Sync libraries in async tools.** Tool functions are `async`. Blocking/synchronous clients (e.g. the Stock tool's `requests` and `yfinance` calls) must be offloaded with `anyio.to_thread.run_sync(...)` rather than called directly — see `tools/stock_data.py`. `httpx.AsyncClient` is used directly where the library is async-native (web search, Wolfram). The same offload applies to **CPU-bound** work that could stall the single-process event loop: `fetch_page`'s model-supplied `query` regex is run in a thread through the timeout-capable `regex` package. Over-long or nested-quantifier patterns fall back to literal search, and every segment match receives the remaining total scan budget; a timeout raises `ToolError` rather than returning incomplete matches. When several independent blocking calls don't depend on each other, dispatch them concurrently rather than serially: `get_company_data`'s `_gather_sections` fires each section through its own `to_thread.run_sync` and `await`s them together, so a multi-section call pays the slowest provider's latency, not the sum.

**JSON output is centralized.** Structured tool results are serialized through `tools/serialize.py:to_json()` rather than directly with `json.dumps`, which emits **compact** JSON by default (to conserve the model's context window) and **indented** JSON when debug mode is on. Debug mode is a single server-level switch (`server.debug` / `MCP_DEBUG`, on `ServerSettings`): when enabled it also forces DEBUG-level logging and each tool logs its invocation via `log_call(...)` and a result summary via `log_result(...)`. Wrap each tool's `return` with `log_result(log, "<tool>", to_json(payload))`, and call `log_call(log, "<tool>", **args)` at the top of the function. Every tool returns JSON through `to_json` — including Wolfram, whose `query_wolfram_alpha` parses the LLM API's labeled-section plaintext into `{query, data:{…}, assumptions?, url?}` via `_structure_result` (dropping the echoed query, image-URL lines, and folding the verbose "Assuming …" boilerplate into a structured `assumptions` field) so its output matches the other tools' shape. (The YouTube transcript path returns plain text from `fetch_transcript`, which `fetch_page` then wraps in its JSON envelope with `format: "youtube_transcript"`.)

**Tool descriptions and schemas are the model's API.** FastMCP derives them from the `@mcp.tool()` function docstring unless an explicit `description=` is supplied. Keep detailed usage guidance there (query formatting, when-to-use / when-not-to-use, and parameter semantics). Verify the serialized API rather than assuming the source docstring is the final description. Safety annotations are centralized in `tools/tool_annotations.py`: data tools use the read-only/idempotent external profile, while `send_email` uses the non-read-only/non-idempotent external profile.

**Surface configured caps to the model as concrete numbers.** A docstring can't be an f-string, so a cap written as the word "capped" leaves the model guessing the actual limit (and getting silently clamped, or refused). FastMCP lets you inject the live `cfg` value at registration time two ways, and `register(mcp)` runs at startup with `cfg` loaded, so both interpolate real numbers:
- **Per-argument cap** → annotate the parameter with `Annotated[T, Field(description=f"... {cfg.max_x} ...")]`. A `Field` description wins over a `:param:` line, so drop that param's `:param:` from the docstring to avoid a stale duplicate (keep `:param:` for the un-capped params). This is the authoritative place — it's where the model fills in the value. See `find_nearby_places` (`radius_m`/`limit`/`nearby_towns_limit`), `search_web` (`num_results`/`max_tokens`), and `get_company_data` (`periods`/`news_items`/`insider_weeks`/`history_bars`/`news_days`).
- **A number that lives in prose, not on a param** → pass `@mcp.tool(description=...)` a runtime-built string and interpolate there. When you do this, FastMCP still parses `:param:` from the docstring, so slim the docstring to a one-line human pointer plus the `:param:`/return lines and move the model-facing prose (including the `Returns JSON {...}` shape) into the `description=` string; keep the brace-heavy return shape as a plain (non-f) string to avoid escaping. See `find_nearby_places` (towns radius) and `fetch_page` (whose model-facing prose and `Returns JSON {...}` shape live in the `description=` string).

Verify what the model actually receives — the serialized `tools/list` entry, which no longer matches the source docstring — with `python scripts/show_tool.py <tool>` (`--json` for the full schema). Caps come from config, so point the script at a throwaway file to confirm one is genuinely dynamic: `MCP_CONFIG_FILE=/tmp/caps.yaml python scripts/show_tool.py find_nearby_places` (env overrides work too: `GEO_MAX_RADIUS_M=50000 …`). The script builds the real server via `build_server()`, so it covers every tool.

## Web Search support services

`search_web` uses Brave's hosted **LLM Context API**, authenticated by `web_search.brave_api_key`. It returns pre-extracted, relevance-ranked snippets plus source metadata; result count and excerpt tokens are context-budget caps. Brave calls are process-serialized by default with a one-second quiet period, and transient failures use bounded exponential retries that honor Retry-After / Brave rate-limit reset headers; higher-throughput plans can set `web_search.brave_request_delay_seconds: 0`. Brave-native country, result language, freshness, safe-search, and relevance-threshold options replace the former backend categories and pagination, which LLM Context does not support. `fetch_page` separately depends on **FlareSolverr** (first-line HTML renderer), optional **Firecrawl** (final page fallback enabled by `web_search.firecrawl_api_key`), and **Apache Tika** (text extraction for PDF/Office/OpenDocument/RTF/EPUB). An optional small OpenAI-compatible model can classify ambiguous renders when `web_search.classifier_api_url` and `classifier_model` are set. `docker-compose.yml` starts FlareSolverr and Tika; Brave, Firecrawl, and the optional classifier are called through configured API URLs. The non-web tool groups have no local-service dependencies.

`fetch_page` begins with a streamed direct probe. Documents, JSON/XML, plain text, and unsupported binary media finish on that lightweight direct path; HTML closes the probe without downloading the body and goes to FlareSolverr first. A known document that returns an HTML challenge may use Firecrawl's document-to-markdown parser, but is never sent to the HTML browser path or Tika as bogus challenge bytes. A generic structural/content quality gate accepts clear page content and sends blocked or unusable renders to Firecrawl. Ambiguous pages use the optional classifier; without a configured classifier that stage is skipped. Hedged Firecrawl is available but disabled by default; the sequential path separately bounds a FlareSolverr attempt when Firecrawl is configured so one browser stall cannot consume the whole MCP deadline. Repeated failures for distinct URLs on one host open a short-lived circuit that bypasses FlareSolverr. Firecrawl and FlareSolverr HTML use the same BeautifulSoup extraction paths so text, structured, section, and query modes stay consistent. Reddit uses OAuth JSON when `WEB_SEARCH_REDDIT_CLIENT_ID`, `WEB_SEARCH_REDDIT_CLIENT_SECRET`, and `WEB_SEARCH_REDDIT_USER_AGENT` are configured, then falls back through RSS, targeted `old.reddit.com` HTML extraction, and post-only oEmbed metadata. `search_web` returns Brave's excerpts and source metadata without fetching result pages. Models use `fetch_page(mode="structured")` for outlines. Search enrichment and its result-count/download settings have been removed; `WEB_SEARCH_MAX_ENRICH_HEADINGS` retains its historical name solely for fetch_page's heading cap.
